Tokenizer internals — algorithm, not vocabulary

Byte Pair Encoding, running live

The tokenizer is trained once on a text sample, frozen into a vocab table + an ordered list of merge rules, then reused unchanged for every input the model ever sees — however large the training corpus was. This runs the real algorithm on a tiny corpus so every step is visible.

1 — Training corpus

Each word starts as individual characters, plus a boundary marker (·) so the tokenizer can tell "est" at a word's end from "est" in the middle of one.

2 — Word segmentation (live)

3 — Adjacent-pair frequencies

4 — Merge ledger (the frozen rule list)

    This ordered list — not the corpus — is what actually ships with the model. At inference time, encoding new text means replaying these rules in rank order.

    5 — Tokenize new text with the learned rules

    6 — Where the merge rules actually live, on disk

    GPT-2-style tokenizers ship this as two small text files sitting next to the model weights — not inside them. vocab.json maps symbol → id, merges.txt is the ranked rule list, one merge per line, in the exact order they were learned.

    
    
    The Python below builds those two files from this page's own merge ledger, then re-implements encode(): repeatedly scan the word for the pair with the lowest rank in merges.txt and fuse it, until no learned pair remains. It's the same loop as the "Tokenize new text" step above — just in the form it's actually shipped and run.
